## The four fixes — root cause, fix, edge cases, and the deterministic proof for each

> For every fix: the **Repro** must be RED before you change implementation code, and you must paste that red output into the ledger. Then fix. Then the **Proof** must be GREEN, pasted into the ledger. A fix with no red-first repro is rejected — you cannot prove you fixed something you never demonstrated was broken.

### Fix A — Replay-drop race (file as ND-40)

**Root cause (verify, then trust):** `cli/attach.ts` does `await client.connect()` then `runTty()`→`client.subscribe({onBytes})`. In `client.ts`, `socket.on('message')` is registered inside `connect()` but reads `this.callbacks.onBytes` *at message-time*. `connect()`'s promise resolves on `'open'`; the server's `hello`+`replay_start`+**binary screen snapshot** (incl. `\x1b[?1049h`)+`replay_end` can arrive coalesced with the 101 in a single client read, so `ws` emits `'open'` then **synchronously** emits `'message'` for the buffered frames — *before* the `await connect()` continuation runs `subscribe()`. At that instant `onBytes` is `undefined`, so `this.callbacks.onBytes?.(buf)` no-ops and the replayed screen is **dropped**. The server's `setImmediate` (handler.ts ~156) reduces but does not remove the window. Confirmed empirically: real-binary `altScreen` flipped `false` on **2/10** loopback runs.

**Fix (preferred — root cause, makes both orderings safe forever):** in `AttachClient`, buffer inbound **binary** frames that arrive while no `onBytes` subscriber exists; flush them, in arrival order, the first time `onBytes` transitions `undefined → defined` (in `subscribe()` or via the constructor callbacks). After a subscriber exists, never buffer — deliver directly.

**Edge cases you MUST cover (each becomes a test assertion):**
- **Order preserved** across ≥2 buffered binary frames.
- **No double-delivery**: a frame that arrives *after* subscribe is delivered exactly once, never also flushed from the buffer.
- **onBytes set at construction** (not via subscribe): no buffering, direct delivery — no regression for that path.
- **Idempotent subscribe**: calling `subscribe({onBytes})` twice flushes the buffer exactly once (only on the undefined→defined transition).
- **Text frames in the gap** (`hello`/`replay_start`/`replay_end`) still process normally (they set `this.hello` / call their own callbacks) — only `onBytes`-bound binary frames buffer.
- **Bounded buffer**: cap the buffer at `replayBufferBytes` (align with the server's ring-buffer cap, read from `hello`); never grow unbounded if a caller never subscribes. Document the cap with an ND-40 citation.
- **Live bytes vs replay**: bytes arriving after `replay_end` but still before subscribe (shouldn't happen in production, but defensively) use the same buffer and same ordering.

**Reject the alternative (reorder `cli/attach.ts` to subscribe-before-connect) as the primary fix** — it engages raw mode + attaches stdin listeners before `connect()`, so a connect failure (ECONNREFUSED → `return 2`) would leave the terminal in raw mode with no cleanup path (runTty exposes only `done`, not `cleanup`). You may add it as *defense-in-depth* later, but the buffer is the correct root-cause fix. Record this rejection in ND-40.

**Repro (deterministic — this is the anti-guess-and-check core):** a co-located unit test in `client.test.ts` using the `wsFactory` seam. Build a fake `ws` that, on a `setImmediate` after `connect()` has registered its handlers, **emits `'open'` then synchronously emits a binary `'message'`** (the alt-enter + a recognizable payload) in the *same* callback. Drive the client in **production order**: `await client.connect()`, *then* `client.subscribe({ onBytes })`, then flush microtasks.
- **Pre-fix assertion (RED):** captured bytes are **empty** — the frame was dropped. This must fail-by-dropping deterministically (run it 50× via `vitest --repeat 50` or a loop; it must drop 50/50, proving it's not luck).
- **Post-fix assertion (GREEN):** captured bytes **equal** the payload, in order; 50/50.

**Proof (integration, quantified):** after Fix D switches `spawnHarnessClient` to production ordering, run `pnpm tui:capture` **20×** and assert the in-process **and** real-binary during-attach captures report `altScreen=true` **20/20**. (Pre-fix, the real binary flaps ~20% — so 20/20 is a meaningful bar, not a tautology.) Use the loop in [Validation ledger](#validation-ledger).

### Fix B — ND-38 overlay (screen not restored on close)

**Root cause:** `runTty`'s `cleanup()` only does `enableRaw(false)`; it never leaves the alt-screen the agent entered (via PTY passthrough). On close, `onClose` runs `cleanup()` then writes the `[relay] …` line — which lands painted into the frozen agent frame. Fires on **every** close path, including `session_ended` (per the ND-38 doc), not just `^D`.

**Fix:** in `cleanup()`, before the `[relay]` line is written, emit a conservative terminal reset to **stdout** — minimally exit the alternate screen + sane defaults (`\x1b[?1049l` then `\x1b[0m`; consider also `\x1b[?25h` to restore the cursor the fixture/agent may have hidden). Emit it on **every** close path. Cite ND-38 in the comment.

**Edge cases you MUST cover:**
- **Non-TUI / line-oriented agent unharmed**: an agent that never entered alt-screen must, after detach, still show its primary-screen output intact — `\x1b[?1049l` must be a no-op there, not a screen-clear. Add a scenario whose fixture **never** emits `\x1b[?1049h` and assert the primary-screen content survives the reset.
- **`session_ended` path**: add a scenario that ends the session server-side (kill it) so the client receives `session_ended` → close; assert the screen is restored there too (the current harness only tests `^D`).
- **Ordering**: the reset (stdout) must precede the `[relay]` line (stderr) — `captureCombined()` (stdout∥stderr) must show a clean primary screen with the `[relay]` line on it, `altActive===false`.
- **No regression to messaging**: the ND-34 `localDetach` latch and the "still running" vs "session ended" wording stay exactly as-is.

**Repro (deterministic, in-process — reliable because in-process subscribes first):** the existing `it.fails` guard in `tty-visual.test.ts` asserts `after.altActive===false`. It currently passes *because it's marked `.fails`* (the bug makes it true). Pre-fix: confirm removing `.fails` makes it **RED** (`altActive===true`). Post-fix: it is **GREEN** and stays de-`.fails`'d as a permanent regression test. Add the byte-level companion: assert `cleanup()`'s stdout contained `\x1b[?1049l` before the `[relay]` text.

**Proof:** the de-`.fails`'d overlay guard passes; the new non-TUI-agent scenario passes; the new `session_ended`-close scenario passes; `nd38-after-detach.txt` now reports `altScreen=false`.

### Fix C — ND-38 hang (process never exits on raw-mode `^D`)

**Root cause:** in raw mode `^D` is a `0x04` data byte → `client.close()` (socket closes) but stdin is never paused/unref'd and its listeners stay attached, so a flowing ref'd TTY stdin keeps the event loop alive → the process hangs. `cli/relay.ts` sets `process.exitCode` but never `process.exit` on a clean detach.

**Fix:** pick ONE of the ND-38 menu options and justify it in the Resolution. Recommended: release stdin in `runTty`'s `cleanup()` (`stdin.pause()`, remove the `data`/`end` listeners, `stdin.unref?.()`) so a clean event-loop drain exits naturally and preserves `process.exitCode` semantics — every caller benefits. Cite ND-38.

**Edge cases you MUST cover:**
- **Flush-before-exit**: if you choose `process.exit` (option b) instead of natural drain, you MUST drain stdout first or the Fix-B reset bytes + the `[relay]` line get truncated. Validation must confirm BOTH that the process exits AND that the screen-restore bytes actually reached the terminal. (This coupling is why natural-drain via stdin release is recommended over `process.exit`.)
- **Canonical-mode path not regressed** (ND-25(b)): the `'end'`/EOF single-press detach must still exit; `client.close()` stays idempotent across `data` + `end`.
- **No double-cleanup**: `cleanup()` is already guarded by `cleanedUp`; keep it.

**Repro (real binary — the ONLY path that can show a process hang; in-process can't):** `spawnRealAttachClient` + `^D` + wait. The current test asserts `real.hasExited()===false` (hang reproduced). Pre-fix: that assertion is GREEN (hang present) — paste it. Post-fix: **invert** it — assert `real.exited` resolves within 2 s (`await Promise.race([real.exited, timeout(2000)])` resolves via `exited`, and `real.hasExited()===true`). This MUST run against **FRESH dist** (see Fix D / Preflight #1) or it tests old code.

**Proof:** the inverted real-binary test passes; run it **10×** (real PTY timing) and it exits promptly **10/10**; vm-e2e confirms a real `relay attach` on the VM returns to the shell prompt on a single `^D` with no follow-up `^C`.

### Fix D — Make the tui-visual harness faithful (so this can't silently regress)

**Root cause of the infidelity:** `spawnHarnessClient` subscribes **before** connect (tty-harness.ts ~223-242) specifically to guarantee replay capture — which masks Fix A's race. And nothing asserts `altActive` on the real-binary path, so its ~20% flap is silent. And `distCliBuilt()` only `existsSync` → tests stale `dist/`.

**Fix:**
1. **Production ordering**: rewrite `spawnHarnessClient` to `await client.connect()` **then** `runTty(...)` (subscribe), mirroring `cli/attach.ts` exactly. After Fix A this is deterministic; before Fix A it would flap (that's correct — the harness should reflect reality).
2. **Real-binary during-attach altActive assertion**: add a capture taken *during* attach (before any detach) that asserts `altActive===true`. This converts the silent flap into a real guard.
3. **Freshness guard**: replace `distCliBuilt()` (existsSync) with a check that the newest mtime under `src/attach/` + `src/cli/` is ≤ the `dist/cli/relay.js` mtime; if stale, **fail loud** with a "run `pnpm -F @relay/relay build`" diagnostic (or wire a `pretui:capture` build step). Never silently skip on stale.

**Edge cases:**
- The freshness guard must still `describe.skip` cleanly (with a clear reason) when `dist/` is **absent** (fresh checkout, no build) — absence is skip, **staleness** is fail.
- Don't break the `spawnHelperReady()` gate.

**Repro / Proof:** touch a source file under `src/attach/`, run `pnpm tui:capture` → the freshness guard must report STALE / fail, not pass. Rebuild → green. With production ordering + Fix A, the 20/20 in-process **and** real-binary `altScreen=true` proof from Fix A holds.
