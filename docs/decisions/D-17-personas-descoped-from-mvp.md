# D-17 — Personas descoped from MVP (deferred to Phase 2)

**Surfaced by:** User decision 2026-05-28 — a deliberate descope of the MVP to center on the remote-coding-session core (host → attach → render → claim/release). Personas were a stable, implemented MVP requirement; the user chose to put the module dormant rather than carry persona UX through the start-session flow while UX/UI stabilizes.

## Question

Should personas remain a Phase 1 (MVP) deliverable, or should they be descoped — removed from every user-reachable path so the MVP centers on the remote coding session — while leaving the implemented module in the tree for a Phase 2 re-enable?

## Context

Personas were added to the MVP PRD as a core requirement and are implemented in a stable state: the `persona/` module (loader, validator, composer), the `@relay/protocol` persona schemas, four pure-persona unit tests, and seven default YAMLs all ship. The persona path threads through session spawn (`--append-system-prompt` / `--model` / `--mcp-config` / `--strict-mcp-config` / `--disable-slash-commands`), the `/personas` REST routes, the `relay persona list/create` CLI, `relay init`'s default-persona seeding, and the IDE extension's persona picker in the start-session flow.

The remote-session core is already stable and MVP-ready: ND-38 (clean-detach hang) and ND-40 (replay-drop race) are fixed and the cross-device `vm-e2e` real-LAN proof passes. Of the Phase 1 acceptance scenarios, only **Scenario B** is persona-specific; **A, C–G** pass without personas once G drops its "(project, persona)" phrasing and C drops "with a chosen persona."

The descope is **decoupling, not deletion**: the user wants the persona module asleep (still in tree, still unit-tested in isolation, one-line-revert re-enable in Phase 2), with no user-reachable path able to exercise it. The risk to manage is **accidental re-coupling** — a dangling `Persona`-typed export on the live spawn path, a silently re-registered `/personas` route, or a client-routable `personaName` parameter.

## Options under consideration

- **Option A — Dormant module + server-stamped `personaName` sentinel.** (Chosen.) Cut the user-reachable persona *path* but keep the `personaName` *field* everywhere it is already plumbed (DB column, store row, `SpawnRecord`, wire `SessionSchema`, CLI rows, extension `Session`). The server stamps a fixed sentinel (`'agent'`) at session insert; it is never user-supplied. Avoids a DB migration (the `NOT NULL` column keeps a valid value), keeps row/wire types and `.strict()` contracts unchanged, and makes the session display-label change cosmetic. `buildArgv`/`hashPersonaFile` are **deleted** from the live spawn module (the likeliest re-coupling point); the `persona/` module and the protocol persona schemas stay exported but dormant.
- **Option B — Delete the persona module and the `personaName` column.** Rip out `persona/`, the schemas, the column, and the field. Cleanest end state, but requires a destructive DB migration, churns row/wire types and every `.strict()` contract, deletes refactor-safe unit-tested code, and turns the Phase 2 re-enable from a one-line revert into a re-implementation. Throws away working code for a feature that is deferred, not cancelled.
- **Option C — Leave personas wired but hide the UI.** Keep the spawn path and routes; just remove the extension picker and default a persona server-side. Lowest diff, but leaves `/personas` reachable, leaves a client-routable `personaName` on the create path, and leaves the persona spawn overlay live — so "not invokable" is unenforced and the re-coupling surface stays wide open.

## Current thinking

Option A. Keeping the field as a server-stamped sentinel is the lowest-risk, most-reversible cut: it removes the user-reachable persona path (the actual goal) while leaving the data shape and the dormant module intact for Phase 2. Deleting `buildArgv`/`hashPersonaFile` (rather than leaving them dormant) closes the most likely accidental-re-coupling vector, and a `/personas → 404` test guards against silent route re-registration.

## Resolution

**Adopt Option A — personas are deferred to Phase 2; the module goes dormant and sessions spawn a bare agent, with `personaName` retained as a server-stamped sentinel.** The contract:

1. **Bare-agent spawn.** `SessionRegistry.create()` takes no persona and spawns the agent CLI with an **empty argv** — no `--append-system-prompt`, `--model`, `--mcp-config`, `--strict-mcp-config`, or `--disable-slash-commands`. `SessionCreateInput` has no `personaName` field, so there is no parameter through which a client value could reach the spawn path.
2. **Server-stamped sentinel.** The server stamps `personaName = 'agent'` at session insert. The `sessions.persona_name TEXT NOT NULL` column, the store row, `SpawnRecord` (persona fields now `.optional()` and omitted by the writer), the wire `SessionSchema.personaName: z.string()`, the CLI session rows, and the extension `Session` type are all unchanged — they carry the sentinel. No DB migration.
3. **Not invokable.** No user-reachable path exercises personas: `POST /sessions` accepts `{ projectId }` only; the `/personas` routes are left unmounted (`registerPersonasRoutes` is not called) and return 404; the `relay persona` CLI command is removed; `relay init` seeds no default personas (`~/.relay/personas/` is not created); the extension shows no persona picker and labels sessions by their short id.
4. **Dormant, not deleted.** `packages/server/src/persona/*` and its four unit tests stay in the tree and keep running against the dormant module (refactor-safety for the Phase 2 re-enable). The `@relay/protocol` persona schemas and the seven default YAMLs stay on disk. `routes/personas.ts` and `cli/persona.ts` stay on disk, unimported. `buildArgv`/`hashPersonaFile` are **deleted** from `session/spawn.ts` (not left dormant) because a `Persona`-typed export on the live spawn module is the most likely accidental re-coupling point.
5. **Acceptance gate re-scoped.** Phase 1's gate drops from scenarios A–G to **A, C–G**. Scenario B (persona authoring + selection) is deferred to Phase 2; Scenario C drops "with a chosen persona"; Scenario G's "(project, persona) pairs" becomes "different projects."
6. **Code comments cite D-17.** Every non-obvious persona removal on the live path carries a `// Per D-17` comment so a future reader traces the descope rather than re-deriving it.

**Supersedes-for-MVP.** [[d-06-persona-inheritance]], [[d-09-persona-yaml-schema]], and [[d-g1-persona-application-semantics]] are deferred (until Phase 2) and gain a `Superseded-for-MVP by D-17` line; [[nd-08-skill-subset-enforcement-mechanism]] is parked under the same trigger (its enforcement question is moot while no persona is applied). The decisions remain correct *as designs* — they are simply not in force at MVP because no persona is loaded.

**Why this and not Option B (delete the module + column):** Personas are deferred, not cancelled. Deleting working, unit-tested code and the `NOT NULL` column would require a destructive migration, churn every row/wire `.strict()` contract, and convert a one-line Phase 2 revert into a re-implementation — all to remove code that is already asleep and costs nothing to keep.

**Why this and not Option C (hide the UI only):** Hiding the picker without unmounting `/personas`, narrowing the create input, and removing the spawn overlay leaves "not invokable" unenforced. A client could still POST a `personaName`, the route would still answer, and the persona overlay would still apply — exactly the user-reachable path the descope is meant to close.
