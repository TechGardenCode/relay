# ND-35 — Diagnostics + error UX deep-dive — painless-rollout bar

**Status:** resolved (2026-05-27)
**Affects:** `docs/prd/03-server.md` §3 (agent spawn + credential validation); `docs/arch/persona-application.md` (persona-load failure surface); `docs/arch/rest-conventions.md` (RFC 9457 problem-details recovery guidance); `packages/server/src/session/` (pre-spawn validation hooks); `packages/extension/` (in-IDE diagnostics surface — log access, failure notices, "why is this broken" affordances).
**Surfaced by:** [[d-15-ux-rollout-posture]] resolution (2026-05-22). One of four per-surface deep-dives opened to gate Phase 1.5 rollout.

## Question
What is the minimum painless-rollout bar for **diagnostics and error UX** — the visibility a user has into "what's failing and why" when something goes wrong? Today many failure modes are silent (bad credentials, missing persona files, project-marker mismatches), generic ("session ended"), or invisible from the IDE (server-side logs require SSH). Which diagnostic surfaces must exist before a non-author user can recover from a failure without DMing the author?

## Elaboration prompt
The inventory in [`docs/arch/ux-rollout-posture.md`](../arch/ux-rollout-posture.md) §6 lists what's painful today. The resolution must decide which items are P0, P1, or deferred-with-rationale.

**What to consider:**

- **(a) Pre-flight credential validation per [[d-10-agent-model-credentials-handling]] / [[nd-19-claude-login-oauth-as-the-documented-credential-default-anthropic-api-key-as-fallback]].** Today if `ANTHROPIC_API_KEY` is invalid or `claude login` was never run, the agent process spawns and may silently fail or hang. Relay does not validate credentials before spawning. The operator discovers the failure only when attaching and seeing the agent exit or produce no output. Decide whether `relay server` boots with a credential probe (call `claude` with `--version` or a no-op invocation, check exit), whether `POST /sessions` rejects with a 5xx + RFC 9457 problem-details before spawning if credentials are missing, or whether the validation runs at `relay init` time.

- **(b) Persona-load failure visibility per [[d-g1-persona-application-semantics]] / [[nd-11-agentsessionid-capture-mechanism]].** Per the persona-application doc, if a persona YAML has a syntax error or MCP config mismatch, the session spawns but the persona is not applied — the failure is "non-fatal." A user sees normal agent output but `agent_session_id` stays `NULL` and the persona's system prompt is missing. Today there is no surfaced error. Decide whether: (i) persona-load failures become fatal (session refuses to spawn with a clear error), (ii) persona-load failures surface as a session-record field that the IDE renders ("persona did not apply: <reason>"), or (iii) the `persona-yaml-check` skill (removed with the persona code at tag `pre-cleanup-phase1`; restore in Phase 2) is wired into `relay server` boot to fail-fast before any session is started.

- **(c) REST error recovery guidance per [`docs/arch/rest-conventions.md`](../arch/rest-conventions.md).** Errors are RFC 9457 problem-details with machine-readable `type` codes (`project-path-taken`, `project-slug-undeducible`, etc.) but the docs do not describe the recovery path. A user receives `409 project-slug-undeducible` with no guidance on "what slug will work" or "how to fix the path you passed." Decide whether: (i) each `type` code gains a `recovery` field in the problem-details payload (machine-readable next-action), (ii) each `type` code documents its recovery path in `docs/arch/rest-conventions.md` so the IDE extension can hard-code the user-facing copy, or (iii) the recovery copy lives in the IDE extension's error-handler with a fallback for unknown codes.

- **(d) Log access from the IDE.** Today the server's stderr (where spawn failures, persona-load errors, and other "why is this broken" data live) is visible only to whoever started `relay server`. A user on a different device has no in-IDE way to see "why did my session not start?" Decide whether the IDE extension contributes a "Show server logs" command (REST route returning the last N log lines), a tail-style WebSocket log stream (gated by tenant ownership), or whether the docs commit to "SSH to the server box to see logs" as the documented path.

- **(e) "Why is this broken" diagnostics from the IDE.** When `relay attach` exits unexpectedly (auth_expired, session_ended, BUSY rejection, server unreachable), the terminal pane just closes. Decide whether the extension intercepts the exit code (via `vscode.window.onDidCloseTerminal`?) and surfaces a notification or an output-channel entry explaining what happened, with a "reconnect" or "see logs" action.

- **(f) Silent terminal-close on attach failure.** Today `vscode.window.createTerminal({ shellPath: 'relay', shellArgs: ['attach', sid, ...] })` opens a terminal pane that prints any `relay attach` stderr inline before exiting on failure. A user not watching the pane misses the stderr entirely. Decide whether the extension wraps the spawn in a way that captures stderr and surfaces it as a notification on non-zero exit, in addition to the inline pane output.

- **(g) `relay doctor` subcommand.** Decide whether `relay doctor` ships (or `relay init --check`) — a single command that probes everything: credentials present, server reachable, token valid, persona files parse, `claude` binary on PATH, SQLite writable. Useful for new-install troubleshooting; overlaps [[nd-32-install-and-onboarding-deep-dive]] (g) version banner.

- **(h) Project-marker mismatch error UX per [[nd-07-marker-file-schema]].** Today a marker carrying an unknown `schemaVersion` causes the extension to refuse-to-bind silently (per [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]]). Decide whether the refusal surfaces as a clear "this project was registered with a newer/older Relay; upgrade [the server | the extension]" notice with a remediation action.

- **(i) Telemetry / failure reporting (out-of-scope flag).** Flagged here so the deep-dive consciously punts unless the resolution scopes it in.

- **(j) Audit-log surface.** Auth events, session spawns, project-add events go to the SQLite store but have no user-facing surface. Decide whether ND-35 introduces `relay audit` or whether audit is deferred to Phase 3 hardening.

**Validation against the gate.** The resolution must end with a line of the shape "the painless-rollout bar for diagnostics + error UX is: <one-paragraph statement>" so [[d-15-ux-rollout-posture]] §7 can quote it.

This is filed as `open` so the resolution lands as a deliberate deep-dive (Track 7E in `docs/build-plan.md`) rather than inline drift.

## Resolution

**Ship one read-only diagnostic command — `relay doctor` — that turns the silent-failure class into actionable text, document REST recovery paths so a client can render "what to do next," and defer every heavier diagnostic affordance (pre-spawn credential gate, machine-readable `recovery` field, in-IDE log access, attach-exit notifications, marker-mismatch notice, `relay audit`) as P1/Phase-3 with rationale.** The frame is the same one the sibling deep-dives [[nd-32-install-and-onboarding-deep-dive]] and [[nd-34-session-and-attach-polish-deep-dive]] used: a decision-first deep-dive ships exactly the cheap, source-install-independent lever that helps a non-author *today* and names everything else as deferred-with-rationale rather than half-building it. For diagnostics, exactly one lever carries that weight and is cheap: a single command a stuck user can run to learn *why* nothing works. `relay doctor` subsumes the credential, binary, persona-parse, storage, and reachability checks that items (a), (b), (g) each gesture at, and it is pure CLI — no extension surface, no new wire protocol, no schema migration, runnable on the same source-install path that exists now. Everything else either depends on a still-open sibling ND (ND-30 attach event-stream, ND-31 multi-server keying), or is a multi-surface feature whose absence does not stop a non-author from recovering.

**No resolved contract is changed by this resolution.** Persona-load stays non-fatal per [[d-g1-persona-application-semantics]] (`relay doctor` *reports* parse failures; it does not make them fatal, and `relay server` boot still excludes-not-crashes on a bad persona per [[d-09-persona-yaml-schema]] §4). Credentials stay server-level env pass-through per [[d-10-agent-model-credentials-handling]] / [[nd-19-claude-login-oauth-as-the-documented-credential-default-anthropic-api-key-as-fallback]] (`relay doctor` *probes* presence, never stores or re-architects). The marker refuse-to-bind rule per [[nd-07-marker-file-schema]] is untouched. Because nothing flips a resolved decision, no new D-NN is filed.

### Per-item (a)–(j) triage

- **(a) Pre-flight credential validation — P0 *as a `relay doctor` probe*; pre-spawn `POST /sessions` rejection deferred P1.** `relay doctor` checks credential **presence** against both paths [[nd-19-claude-login-oauth-as-the-documented-credential-default-anthropic-api-key-as-fallback]] names: `ANTHROPIC_API_KEY` in the environment, or the `claude login` OAuth surface (the `Claude Code-credentials` Keychain entry on macOS, `~/.claude/.credentials.json` on Linux). This catches the single most common silent failure — "never authenticated" — and prints `claude auth login` / `ANTHROPIC_API_KEY` remediation. Wiring the same probe into `POST /sessions` to **reject before spawn** is deferred P1: it is `session/`-path code with platform-specific credential detection in the hot path, and a presence check cannot catch an *invalid* key or *expired* token (validity still surfaces only at the agent), so it would convert one silent failure into a partial gate at non-trivial cost. Re-open trigger: silent-hang reports persist after `relay doctor` plus the [[nd-32-install-and-onboarding-deep-dive]] onboarding reminder have shipped. The chosen option is the deep-dive's "(g) probes both paths, doesn't store"; the rejected option is "boot-time `relay server` probe that hard-fails the whole server," which would down the server for an operator who intends headless `ANTHROPIC_API_KEY` use the probe might not see in a launchd environment.

- **(b) Persona-load failure visibility — P0 *as a `relay doctor` persona-parse probe*; the fatality change deferred / declined.** `relay doctor` runs the tenant persona directory through the same loader the server uses ([`loadPersonasFromDirectory`](../../packages/server/src/persona/loader.ts)) and lists any file that fails to parse/validate with its `PersonaLoadReason`, so a YAML typo is a named diagnostic instead of an invisible exclusion. The deep-dive's options (i) "make persona-load fatal" and (ii) "session-record field the IDE renders" are **not** taken: (i) would change [[d-g1-persona-application-semantics]]'s non-fatal contract (a new decision the kickoff explicitly says not to bury here, and undesirable — one bad persona file should not refuse to boot the server), and (ii) is a `@relay/protocol` + REST + store + two-client fan-out for a rare failure, exactly the half-built-feature outcome the rollout frame warns against. Note the existing surfaces already partly cover this: `relay persona list` already prints invalid files to stderr (see `cli/relay.ts`), and the `~/.relay/sessions/<sid>/spawn-record.json` audit ([[nd-12-spawn-json-schema-location]]) records the resolved persona. `relay doctor` makes the parse check a one-command probe; the richer "persona did not apply" session field stays deferred.

- **(c) REST error recovery guidance — P0 *as documentation*; machine-readable `recovery` field deferred P1.** Each `type` code in [`docs/arch/rest-conventions.md`](../arch/rest-conventions.md) gains a documented recovery path (the deep-dive's option ii), giving both the IDE error-handler and a human reader an authoritative "what to do next" keyed on the slug. The deep-dive's option (i) — a machine-readable `recovery` field on the problem-details payload — is deferred P1: the payload schema already `passthrough()`es extension members so the field can be added without a breaking change *when there is a consumer*, but the IDE error-rendering that would consume it is itself deferred (see (e)/(f)), so shipping the field now buys a JSON key only a raw-curl user would read. Option (iii) — recovery copy hard-coded in the extension — is the natural future consumer and reads from the same documented table.

- **(d) Log access from the IDE — deferred P1.** A "Show server logs" REST route + in-IDE viewer is a genuine nicety but high fan-out: a server-side log ring buffer, a new authenticated REST route (or a tenant-ownership-gated WS tail), and an extension command — a security-surface addition (log content can leak across the tenant boundary) for a need that `relay doctor` plus documented errors already cover for the common cases. MVP path stays "access the `relay server` host's stderr" (documented in handbook Ch 7). Re-open trigger: remote-only operators report that `relay doctor` on the server host is not reachable enough.

- **(e) "Why is this broken" diagnostics from the IDE — deferred P1, gated on [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]].** Intercepting `relay attach`'s exit (`vscode.window.onDidCloseTerminal`) to surface *why* the session ended (auth_expired vs session_ended vs BUSY vs unreachable) requires the structured stderr event-stream ND-30 specifies — without it the extension sees only an exit code, not a reason. This is the same dependency [[nd-33-ide-gui-overhaul-deep-dive]] flagged for the anchored BUSY notice. Explicit coupling: **(e) cannot ship a reason-aware notice until ND-30 resolves.** A generic "session terminal closed — run `relay doctor`" notice is possible today but is extension-surface work tracked with the ND-33 polish backlog, not rollout-blocking.

- **(f) Silent terminal-close on attach failure — deferred P1, gated on [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]].** Same coupling as (e): capturing `relay attach` stderr and surfacing it as an IDE notification on non-zero exit needs the structured stream to render anything better than the raw inline pane output that already exists. Note [[nd-34-session-and-attach-polish-deep-dive]] already shipped the *CLI-side* clean-detach confirmation (`detached … the session is still running`), which removes the "did I kill it?" doubt on the terminal surface; the IDE-side notification is the deferred remainder.

- **(g) `relay doctor` subcommand — P0, THE shipped code.** A single read-only command that probes the whole local surface and prints a remediation line per failing check: `~/.relay/` initialized + writable, `config.yaml` parses, an active token store exists, the `claude` binary resolves on `PATH`, credentials present (item a), tenant personas parse (item b), and — when a token is available via `RELAY_TOKEN`/`--token` — the server is reachable with a valid token (any HTTP response proves reachability; `401` means a bad token; a transport error is a WARN, since `doctor` is usually run while the server is down). Exit `0` when every probe is OK or WARN; non-zero when any probe FAILs, so it is scriptable. **Coordinates with [[nd-32-install-and-onboarding-deep-dive]] (g) without duplication:** `relay doctor` prints the local `relay --version` as a header line only; the extension↔server *version-skew banner* ND-32 names stays Track-8 / [[nd-33-ide-gui-overhaul-deep-dive]] work — `doctor` probes presence/validity, the banner compares versions. Motivated directly by [`docs/phase-0-report.md`](../history/phase-0-report.md) surprise #1 (the opaque `posix_spawnp failed.` from a missing `node-pty` exec bit): `relay doctor`'s `claude`-on-PATH and storage probes are exactly the class of pre-flight that turns that into a named cause (the permanent fix for #1 itself remains 6J/Track-8's postinstall, not re-solved here).

- **(h) Project-marker mismatch error UX — deferred P1, gated on extension surface + [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]].** The refuse-to-bind *rule* per [[nd-07-marker-file-schema]] is correct and stays unchanged; the gap is a user-facing "this project was registered with a newer/older Relay; upgrade [server | extension]" notice, which is extension-surface work. It intersects ND-31's still-open multi-server keying (the "upgrade the server" branch presumes the single-server keying ND-31 may revise), so per the kickoff this resolution **notes the dependency and does not pre-empt ND-31**. `relay doctor` cannot reliably cover this — in the true cross-device case the marker lives on the IDE filesystem, not the server host where `doctor` runs.

- **(i) Telemetry / failure reporting — deferred, out of posture.** A self-host single-user product does not phone home; this matches [[nd-32-install-and-onboarding-deep-dive]] (h). No telemetry ships in Phase 1.5. Re-open only if a hosted/managed Relay offering appears with a coherent opt-in owner.

- **(j) Audit-log surface — deferred to Phase 3 hardening.** Auth/session/project events persist in SQLite but get no `relay audit` surface now. It is a forensic/security surface, not a failure-recovery one — a non-author recovering from a broken session does not need an event log, and `relay session show` already exposes `terminatedReason` for the "what happened to this session?" case. Defer with [[d-05-per-device-token-rotation]]-class Phase-3 hardening.

### Contract

1. **One P0 code deliverable: `relay doctor`** (`packages/server/src/cli/doctor.ts` `runDoctor()` → `DoctorReport`, rendered + exit-coded by `cli/relay.ts`), a read-only probe set with a remediation line per failure, covered by `cli/doctor.test.ts`. It is the only shipped diagnostics code in 7E. No `session/` hook, no `@relay/protocol` change, no schema migration, no extension code.
2. **`relay doctor` is read-only and dependency-light.** It performs file-existence/writability/parse/PATH/credential-presence/HTTP-reachability probes only; it does not open the SQLite DB (so it carries no `better-sqlite3` native dep, honoring the [[nd-18-lazy-load-cli-dispatcher-contract]] thin-client posture) and never mutates `~/.relay/`.
3. **Credential probe checks presence on both [[nd-19-claude-login-oauth-as-the-documented-credential-default-anthropic-api-key-as-fallback]] paths**, never validity-by-API-call, and never stores or logs a credential value.
4. **REST recovery guidance lives in `rest-conventions.md`** as documented per-`type` recovery paths (item c, option ii). The machine-readable `recovery` problem-details field (option i) is deferred until an IDE consumer exists; the `passthrough()` schema already permits adding it non-breakingly.
5. **No resolved contract is changed.** [[d-g1-persona-application-semantics]] (persona-load non-fatal), [[d-10-agent-model-credentials-handling]] (env pass-through, never persisted), [[nd-07-marker-file-schema]] (refuse-to-bind) all stand. No new decision is filed.
6. **Deferred items name their gate.** (a-rejection)/(d) are P1 cost-deferrals; (e)/(f) are gated on [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]]; (h) is gated on the extension surface + [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]]; (i)/(j) are out-of-posture / Phase-3.

**Why this and not "ship the pre-spawn credential gate too":** rejecting `POST /sessions` on missing credentials is the most tempting P0 because the silent-hang is the headline failure, but it lands platform-specific credential detection in the session hot path while only catching the *absent* case (a set-but-invalid key or expired OAuth token still spawns and fails at the agent) — a partial gate at real cost, when `relay doctor` already gives the stuck user a one-command answer and the ND-32 onboarding bridge already tells them to authenticate first. **Why this and not "decision-only, defer all code":** the diagnostics surface is the one rollout surface whose entire point is a *tool*, and the handbook already forward-references `relay doctor` in two places; deferring it would leave the silent-failure class (no credentials, `claude` not installed, persona typo, unreachable server) with no recovery affordance at all, which is precisely the "DMing the author" outcome the bar exists to prevent. The chosen scope ships the single highest-leverage, lowest-risk, source-install-independent lever and names every heavier affordance as P1/gated/Phase-3.

**Surfaces new sub-questions:** none — (e)/(f) route to the existing [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]], (h) to [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]], and (a-rejection) carries a re-open trigger rather than a new entry.

**the painless-rollout bar for diagnostics + error UX is: a non-author who hits a failure can self-diagnose and recover with one command — `relay doctor` probes the whole local surface (`~/.relay/` initialized and writable, `config.yaml` parses, an active token store exists, the `claude` binary is on `PATH`, Claude credentials are present via either `ANTHROPIC_API_KEY` or the `claude login` OAuth surface, tenant personas parse, and the server is reachable with a valid token) and prints an actionable remediation line for every failing probe, so the common silent failures (no credentials, `claude` not installed, a persona-YAML typo, an unreachable server, a bad token) surface as text to act on instead of a hung session or a generic error, while REST errors carry documented recovery paths per `type` code in `rest-conventions.md` so a client can render "what to do next"; the heavier diagnostic affordances — a pre-spawn credential gate on `POST /sessions`, a machine-readable `recovery` field on the problem-details payload, in-IDE server-log access, attach-exit notifications, the project-marker-mismatch upgrade notice, and a `relay audit` surface — are deferred as P1/Phase-3 with documented rationale (several gated on the still-open ND-30 attach event-stream and ND-31 multi-server keying), none of them blocking a non-author's ability to recover from a failure without DMing the author.**
