# ND-33 — IDE GUI overhaul deep-dive — painless-rollout bar

**Status:** resolved (2026-05-26)
**Affects:** `docs/prd/04-ide-extension.md` (the extension command surface and GUI affordances); `packages/extension/src/commands/` (the four palette commands); `packages/extension/src/statusBar.ts` (focus-following indicator that today is a single click target); the user's discovery and management of sessions through the IDE rather than the CLI.
**Surfaced by:** [[d-15-ux-rollout-posture]] resolution (2026-05-22). One of four per-surface deep-dives opened to gate Phase 1.5 rollout.

## Question
What is the minimum painless-rollout bar for **IDE GUI** — the visual surface that lets a user discover, attach to, switch between, and manage sessions without reaching for the command palette or the CLI? Today the extension contributes four palette commands and a single-click status-bar widget; everything else falls through to `relay attach` running inside a terminal pane. Which GUI affordances must exist before a non-CLI user can use Relay productively?

## Elaboration prompt
The inventory in [`docs/arch/ux-rollout-posture.md`](../arch/ux-rollout-posture.md) §4 lists what's painful today. The resolution must decide which items are P0, P1, or deferred-with-rationale. The triage frame below covers the known surface.

**What to consider:**

- **(a) Sessions tree view (Activity Bar).** Today there is no Activity Bar contribution — no left-rail icon, no tree view of "sessions in this project" or "all running sessions across all projects." A user with three running sessions has no GUI way to see them; the command palette quick-pick is the only path. Decide whether the extension contributes a `viewsContainers` + `views` entry with at least: sessions-grouped-by-project tree, per-session quick actions (attach, release, kill), live status (running / idle / killed) per [[d-11-server-restart-and-session-orphaning]]. Validate against `vscode.window.createTreeView` API capabilities (refresh on REST poll vs. WS push from the extension itself — though [[d-g2-multi-client-input-arbitration]] forbids WS in the extension; the tree refresh would have to be REST poll).

- **(b) Persona picker UI beyond the quick-pick.** Today "Relay: Start session" surfaces personas via `vscode.window.showQuickPick`. For a user with five personas, this is fine; for a user with twenty (post-`personas/` directory growth), search/filter and per-persona descriptions become necessary. Decide whether the persona picker becomes a tree view, a webview-panel picker, or stays as quick-pick with `matchOnDescription: true` + grouping.

- **(c) BUSY notice anchoring per [[nd-02-rejection-ux-for-busy-response]].** Today the BUSY signal is the unstructured stderr line in the terminal pane (fails ND-02). [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]] is the unblocking dependency: once `relay attach` ships a structured `RELAY-EVENT busy\n` sentinel, the extension can render an ND-02-compliant status-row-anchored, auto-dismissing notice. Decide here: is the IDE GUI overhaul resolution **blocked on ND-30** (so 7C requires 6L-style precursor work on the attach client), or does the GUI overhaul commit to a fallback UX (e.g. status-bar item that turns red on stderr-line detection) for the case where ND-30 ships later?

- **(d) Multi-server pairing UI per [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]].** Today SecretStorage uses single-server keys; a marker pointing at a different server URL refuses to bind. The ND-31 resolution introduces per-server-URL-hashed keys; the GUI overhaul must surface the multi-server picker (which server is this workspace bound to, switch active server, add new server). Decide: does the extension contribute a "server picker" in the status bar, an Activity Bar tree section, or a settings-style webview?

- **(e) Project-marker mental-model gap per [[d-12-project-record-storage-and-relay-project-add-semantics]] / [[d-g6-project-discovery-workspace-to-project-binding]] / [[nd-07-marker-file-schema]].** A CLI-first operator runs `relay project add /path` which today does NOT write the `.relay/project.json` marker (the marker is written server-side during `POST /projects` from the extension). The user opens the IDE, the extension finds no marker, prompts to "register new" or "bind existing," and the user is confused because they thought they already registered. Decide whether (i) `relay project add` writes the marker locally (then the extension just reads it), (ii) the extension's "bind existing" flow always succeeds against the project the CLI registered (by listing all projects for the active tenant), or (iii) the docs commit to one workflow (IDE-first or CLI-first) and the other is a documented friction point. This is a workflow decision, not just GUI.

- **(f) Quick-pick search / filter on attach.** Today "Relay: Attach to session" lists sessions in a quick-pick with no search/filter. A user with ten sessions sees a long list with no way to narrow. Decide whether the quick-pick gains `matchOnDescription` + `matchOnDetail`, grouping by project, or whether attach-via-tree-view (from (a)) supersedes the quick-pick entirely.

- **(g) Subdirectory selection for monorepos per [[d-01-workspace-root-vs-subdirectory-for-start-session]].** D-01 deferred subdirectory selection "if a concrete need surfaces." If the IDE overhaul ships a tree view, the per-project node could expose "start session in this subdirectory" — but D-01 explicitly says no. Decide whether to revisit D-01 here (and refile as resolved with a different choice) or honor the deferral and explicitly note "monorepo subdirectory selection remains deferred per D-01" in the GUI overhaul resolution.

- **(h) Persona switch mid-session per [[d-g1-persona-application-semantics]].** D-G1 makes session personas immutable for MVP; a user wanting a new persona must kill + restart. The GUI could surface a "switch persona" action that kills + spawns a new session with the desired persona while preserving the conversation via Claude Code's native session-resume (Phase 3 per D-G1). Decide whether to surface the kill-and-restart-with-resume gesture in the GUI now (visible affordance, even if it costs the lossy step) or wait for Phase 3.

- **(i) Status-bar richness.** Today the status bar shows `$(broadcast) Relay: <persona>` with a click target running `relay.attachSession`. Decide whether it gains: agent activity indicator (idle / running / waiting), claim-holder indicator (who has the claim, you or another device), unread-output indicator (bytes received since the user last focused the pane), version banner. Each addition costs status-bar real estate.

- **(j) Webview-based session UI (out-of-scope flag).** A full webview-based session UI — chat-style transcript, side-by-side personas, project switcher — overlaps Phase 2 PWA scope. Decide whether the IDE overhaul stays "lightweight tree + status bar + quick-picks" or starts down the webview path. Default is the former; flag the choice explicitly.

**Validation against the gate.** The resolution must end with a line of the shape "the painless-rollout bar for IDE GUI is: <one-paragraph statement>" so [[d-15-ux-rollout-posture]] §7 can quote it.

This is filed as `open` so the resolution lands as a deliberate deep-dive (Track 7C in `docs/build-plan.md`) rather than inline drift.

## Resolution

**Anchor the entire P0 on one affordance — a sessions tree view in the Activity Bar — and let it absorb the discovery, per-session-action, and live-status pain that drives most of items (a), (f), and (i); re-affirm that the project-marker workflow is *already* symmetric (item (e)'s premise was stale); and defer every item gated on an unresolved sibling ND or an existing deferral with named rationale.** This is a **decision-only** resolution: no extension code lands in 7C, so the test-harness preflight (Vitest + mocked `vscode`) is **N/A here** — it becomes the first task of the P0 tree-view follow-up row. The deliberate frame, mirroring [[nd-32-install-and-onboarding-deep-dive]]: ship the single cheapest, highest-leverage GUI lever that works under today's constraints ([[d-g2-multi-client-input-arbitration]] forbids a WebSocket in the extension, so any live surface is REST-poll), and refuse to litigate surfaces whose enabling decision (ND-30, ND-31) or whose deferral (D-01, D-G1) is owned elsewhere.

### Per-item (a)–(j) triage

- **(a) Sessions tree view — P0 (the anchor).** A non-CLI user with N running sessions has *zero* GUI visibility today. The extension contributes a `viewsContainers` + `views` Activity Bar entry carrying a `vscode.window.createTreeView`: sessions grouped by project, each node exposing attach / release / kill quick actions and a live `running` / `idle` / `killed` status badge per [[d-11-server-restart-and-session-orphaning]]. Refresh is **REST poll only** — [[d-g2-multi-client-input-arbitration]] keeps the §5.1 client FSM (and thus the WS) inside `relay attach`, not the extension. This is the one surface that makes "discover, attach, switch, manage without the CLI" true. Ships in a follow-up code row (test harness first).
- **(b) Persona picker beyond quick-pick — P1.** The current `vscode.window.showQuickPick` works at MVP persona counts; it becomes awkward past ~twenty. Cheap win: `matchOnDescription: true` + per-source grouping (tenant vs project). Not a rollout blocker; bundled into the P1 polish row.
- **(c) BUSY anchoring — deferred, blocked on [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]].** An [[nd-02-rejection-ux-for-busy-response]]-compliant anchored, auto-dismissing notice is **not** achievable until `relay attach` emits a structured event stream the extension can consume. The ND-30 architect verdict already rejected stderr-prose-scraping as fragile, so 7C ships **no fallback** that scrapes or pattern-matches stderr. The current human-prose stderr line (`[relay] another device is interacting with this session.`) stays as the documented interim — visible-but-suboptimal, never silent. The BUSY surface is *not* claimable as done until ND-30 lands.
- **(d) Multi-server picker — deferred, blocked on [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]].** A server-picker UI is meaningless until per-server keying is decided. 6I's single-server posture (`relay.serverUrl` + `relay.token`) plus refuse-to-bind-on-URL-mismatch (which honors [[nd-07-marker-file-schema]] rule 5) is the documented Phase-1 limitation; the per-VS-Code-profile workaround stands. No GUI work until ND-31 resolves.
- **(e) Project-marker mental-model gap — re-affirm [[d-12-project-record-storage-and-relay-project-add-semantics]]; the premise was stale.** §4 of [`ux-rollout-posture.md`](../arch/ux-rollout-posture.md) and this ND's elaboration claimed `relay project add` does **not** write the marker. That is false against the current code: `relay project add` (`packages/server/src/cli/project.ts` `runProjectAdd`) calls `POST /projects` — the **same** handler the extension uses ([[d-12-project-record-storage-and-relay-project-add-semantics]] rule 7, "IDE registration parity") — and that handler (`packages/server/src/server/rest/routes/projects.ts`) `mkdirSync` + `writeFileSync`s `<canonicalPath>/.relay/project.json` and appends to `.gitignore` per [[d-12-project-record-storage-and-relay-project-add-semantics]] rule 6 + [[nd-07-marker-file-schema]]. So the CLI **already** writes a marker the IDE reads. No D-12 revision and no follow-up CLI row are needed. The only genuine residual gap is the **true cross-device** topology where the server's filesystem ≠ the IDE's filesystem (so the server-written marker is not on the IDE's disk); in the two documented topologies — same-host, and Remote-SSH where the extension runs in the server context per [`prd/04-ide-extension.md`](../prd/04-ide-extension.md) §3 — there is no gap. The fix is documentation: correct the stale §4/ND-33 framing and note the cross-device residual as a known friction point (overlaps [[nd-35-diagnostics-and-error-ux-deep-dive]]'s marker-mismatch diagnostic).
- **(f) Quick-pick search/filter on attach — P1, superseded as the primary path.** The tree view (a) becomes the primary discovery surface; the status-bar-click → quick-pick path survives as secondary and gains `matchOnDescription` / `matchOnDetail` + project grouping. Bundled into the P1 polish row.
- **(g) Monorepo subdirectory selection — deferred, honor [[d-01-workspace-root-vs-subdirectory-for-start-session]].** A per-project tree node *could* expose "start session in this subdirectory," but D-01 deferred subdirectory selection pending a concrete need, and none has surfaced. Explicitly held deferred per D-01; not revisited here.
- **(h) Persona switch mid-session — deferred, honor [[d-g1-persona-application-semantics]].** Personas are immutable for MVP; the kill-and-restart-with-native-resume gesture is Phase 3 per D-G1. Surfacing a lossy "kill + spawn new" affordance now is premature; deferred to Phase 3 with D-G1's resume.
- **(i) Status-bar richness — split: P1 for REST-pollable, deferred for ND-30-gated.** A REST-poll-derived running-session indicator (e.g. count, or running/idle for the focused root) is a cheap P1 bundled into the polish row. The **claim-holder** indicator (who holds the claim) and a true **agent-activity** (waiting/working) indicator need the same lifecycle event stream as the BUSY notice → those parts are deferred with (c) on [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]]. The tree view (a) already absorbs the "see status" need at P0, so the status bar need not carry it.
- **(j) Webview-based session UI — deferred, out-of-scope.** A chat-style transcript / side-by-side-persona / project-switcher webview overlaps Phase 2 PWA scope ([`prd/05-mobile-pwa.md`](../prd/05-mobile-pwa.md)). The bar stays **lightweight tree + status bar + quick-picks**. Flagged explicitly per the ND's elaboration; revisit only if Phase 2 PWA work surfaces a reusable webview the extension can host.

### Contract

1. **Decision-only resolution.** No extension code lands in 7C. The test-harness preflight (Vitest with a mocked `vscode` module, matching the repo's Vitest-everywhere convention and the subprocess-of-attach "most logic is plain TS" shape) is N/A for 7C and becomes the **first task** of the P0 tree-view follow-up row.
2. **One P0 affordance.** The sessions tree view (Activity Bar `viewsContainers` + `views`, `createTreeView`, REST-poll refresh, sessions-grouped-by-project, attach/release/kill actions, `running`/`idle`/`killed` badges per D-11) is the sole P0 GUI surface. It is buildable today with no blocked dependency.
3. **No WebSocket in the extension.** Per [[d-g2-multi-client-input-arbitration]], the tree view and any status surface refresh by REST poll. The §5.1 client FSM stays in `relay attach`.
4. **BUSY stays prose-interim until ND-30.** 7C ships no stderr-scraping fallback. The human-prose stderr line is the documented interim; the ND-02-compliant anchored notice is gated on [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]].
5. **Multi-server stays single-server-posture until ND-31.** No server-picker UI; refuse-to-bind-on-mismatch ([[nd-07-marker-file-schema]] rule 5) + per-profile workaround is the documented Phase-1 limitation, gated on [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]].
6. **Marker workflow is already symmetric.** `relay project add` writes the marker via the shared `POST /projects` handler ([[d-12-project-record-storage-and-relay-project-add-semantics]] rules 6–7); no code change. 7C only corrects the stale §4/ND-33 "does not write the marker" framing and documents the true-cross-device residual.
7. **Two follow-up code rows.** (i) **P0 tree-view row** — Vitest+mocked-`vscode` harness, then the Activity Bar tree view. (ii) **P1 polish row** — quick-pick `matchOnDescription`/`matchOnDetail`+grouping for persona (b) and attach (f), plus REST-poll status-bar enrichment (i). Both are decision-downstream; neither blocks the rollout bar's *decision*, only its *full UX*.

**Why this and not "ship the full P0 build now":** the rejected full-build scope would have pulled tree-view + picker + status-bar code, plus a from-scratch extension test harness, into a deep-dive whose hard deliverable is a *decision*. The tree view deserves its own row with relay-architect plan-review (against D-G2 REST-poll, ND-02, ND-30/31) and a real harness — cramming it here would under-test the first stateful extension surface. **Why this and not "defer everything":** the tree view has no blocked dependency and is the single affordance that turns "no GUI for sessions" into "manage sessions without the CLI"; naming it P0 (even as a follow-up row) is what lets [[d-15-ux-rollout-posture]] §7 quote a bar that is actually painless rather than "wait for ND-30/31." **Why (e) is re-affirm-not-revise:** the elaboration's "CLI does not write the marker" was stale framing from the 6I e2e walk that predated the 6F `POST /projects` implementation; the code and [[d-12-project-record-storage-and-relay-project-add-semantics]] already agree, so inventing a new CLI marker-write row would have duplicated shipped behavior.

**Surfaces new sub-questions:** none — (c)/(d) route to the existing [[nd-30-relay-attach-stderr-event-stream-for-subprocess-of-attach-consumers]] / [[nd-31-secretstorage-key-namespace-for-multi-server-ide-pairing]]; (e)'s cross-device residual routes to [[nd-35-diagnostics-and-error-ux-deep-dive]]; the P0/P1 code is build-plan rows, not decisions.

**the painless-rollout bar for IDE GUI is: a non-CLI user can discover, attach to, switch between, release, and kill their sessions entirely through a sessions tree view in the Activity Bar — sessions grouped by project, each node carrying attach / release / kill actions and a live running / idle / killed status badge refreshed by REST poll (no WebSocket in the extension, per D-G2). The project-marker workflow is already symmetric — `relay project add` writes `.relay/project.json` via the same `POST /projects` handler the IDE uses (D-12 rules 6–7), so a CLI-registered project binds in the IDE with no "register or bind" re-prompt in the same-host and Remote-SSH topologies; the only residual is the true cross-device case (server filesystem ≠ IDE filesystem), documented as a known friction point. Persona selection and the secondary attach quick-pick gain search/filter and project grouping as P1 polish. The bar explicitly does NOT require: an ND-02-compliant anchored BUSY notice (blocked on ND-30; the human-prose stderr line is the documented interim), a multi-server picker (blocked on ND-31; single-server + refuse-to-bind-on-mismatch is the documented Phase-1 limitation), claim-holder / agent-activity status-bar indicators (deferred with the BUSY surface on ND-30), mid-session persona switching (deferred per D-G1 to Phase 3), monorepo subdirectory selection (deferred per D-01), or any webview-based session UI (out-of-scope; overlaps Phase 2 PWA).**
